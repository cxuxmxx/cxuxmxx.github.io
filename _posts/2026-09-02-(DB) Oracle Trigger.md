안녕하세요. 오늘은 Oracle의 `Trigger`에 대해 정리해보려고 해요.

트리거는 이름 그대로 어떤 이벤트가 발생했을 때 자동으로 실행되는 장치예요. 애플리케이션 코드에서 직접 호출하는 함수나 메서드와 달리, 트리거는 데이터베이스 안에서 특정 조건을 감지하고 스스로 실행돼요.

예를 들어 이런 상황을 생각해볼 수 있어요.

> 주문 상태가 변경되면 변경 이력을 남기고 싶다.
> 회원 정보가 수정되면 수정 시간을 자동으로 갱신하고 싶다.
> 특정 테이블에 데이터가 삭제되면 감사 로그를 남기고 싶다.

이런 로직을 애플리케이션 코드가 아니라 DB 레벨에서 자동으로 처리하고 싶을 때 트리거를 사용할 수 있어요.

---

## Trigger란?

Oracle Trigger는 테이블, 뷰, 스키마, 데이터베이스 등에 특정 이벤트가 발생했을 때 자동으로 실행되는 PL/SQL 블록이에요.

가장 자주 사용하는 건 DML 트리거예요.

DML 트리거는 테이블에 아래 작업이 발생했을 때 실행돼요.

- `INSERT`
- `UPDATE`
- `DELETE`

즉, 데이터를 추가하거나 수정하거나 삭제할 때 DB가 자동으로 정해진 로직을 실행하는 구조예요.

```text
사용자 요청
  -> INSERT / UPDATE / DELETE 실행
      -> Oracle이 트리거 조건 확인
          -> 조건에 맞으면 트리거 실행
```

이 흐름 때문에 트리거는 편하지만, 동시에 조심해서 써야 해요. 코드에서 직접 호출하지 않아도 실행되기 때문에 동작이 숨어 보일 수 있거든요.

---

## 기본 문법

Oracle에서 트리거는 보통 `CREATE OR REPLACE TRIGGER`로 만들어요.

```sql
CREATE OR REPLACE TRIGGER trigger_name
BEFORE | AFTER INSERT | UPDATE | DELETE
ON table_name
[REFERENCING OLD AS old NEW AS new]
[FOR EACH ROW]
BEGIN
    실행할 로직;
END;
/
```

하나씩 보면 어렵지 않아요.

`CREATE OR REPLACE TRIGGER`는 트리거를 생성하거나, 이미 같은 이름의 트리거가 있으면 다시 정의하겠다는 의미예요.

`BEFORE`와 `AFTER`는 트리거가 실행되는 시점을 뜻해요.

- `BEFORE`: 실제 데이터 변경 전에 실행
- `AFTER`: 실제 데이터 변경 후에 실행

그 뒤에는 어떤 이벤트에 반응할지 적어요.

```sql
BEFORE INSERT
AFTER UPDATE
AFTER DELETE
```

특정 컬럼이 변경될 때만 실행하고 싶다면 `UPDATE OF`를 사용할 수 있어요.

```sql
AFTER UPDATE OF status
ON orders
```

이렇게 하면 `orders` 테이블의 `status` 컬럼이 변경될 때만 트리거가 실행돼요.

---

## FOR EACH ROW

트리거를 볼 때 가장 헷갈리는 부분 중 하나가 `FOR EACH ROW`예요.

`FOR EACH ROW`가 있으면 행 레벨 트리거가 돼요. 변경된 행마다 트리거가 한 번씩 실행됩니다.

```sql
UPDATE orders
   SET status = 'CANCELED'
 WHERE created_at < SYSDATE - 30;
```

이 쿼리가 100건의 주문을 변경한다면 어떻게 될까요?

- `FOR EACH ROW` 없음: 트리거 1번 실행
- `FOR EACH ROW` 있음: 트리거 100번 실행

그래서 각 행의 변경 전/후 값을 봐야 한다면 `FOR EACH ROW`가 필요해요.

예를 들어 주문 상태 변경 이력을 남기려면 주문 한 건마다 이전 상태와 새 상태를 알아야 하니까 행 레벨 트리거가 어울려요.

---

## :OLD와 :NEW

행 레벨 트리거에서는 `:OLD`와 `:NEW`를 사용할 수 있어요.

- `:OLD`: 변경 전 값
- `:NEW`: 변경 후 값

이 값들은 `INSERT`, `UPDATE`, `DELETE`에 따라 사용할 수 있는 범위가 달라요.

| 이벤트 | `:OLD` | `:NEW` |
|---|---|---|
| `INSERT` | 없음 | 새로 들어올 값 |
| `UPDATE` | 수정 전 값 | 수정 후 값 |
| `DELETE` | 삭제 전 값 | 없음 |

예를 들어 주문 상태가 `READY`에서 `CANCELED`로 바뀐다면, 트리거 안에서는 이렇게 볼 수 있어요.

```sql
:OLD.status -- READY
:NEW.status -- CANCELED
```

주의할 점은 `OLD`, `NEW` 앞에 콜론을 붙인다는 거예요.

```sql
:OLD.column_name
:NEW.column_name
```

## 예제: 주문 상태 변경 이력 남기기

주문 상태가 변경될 때마다 이력 테이블에 로그를 남기는 예제를 만들어볼게요.

먼저 주문 테이블이 있다고 가정해요.

```sql
CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY,
    customer_id NUMBER NOT NULL,
    status VARCHAR2(30) NOT NULL,
    updated_at DATE NOT NULL
);
```

그리고 상태 변경 이력을 저장할 테이블을 만들어요.

```sql
CREATE TABLE order_status_history (
    history_id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id NUMBER NOT NULL,
    old_status VARCHAR2(30),
    new_status VARCHAR2(30),
    changed_at DATE NOT NULL
);
```

이제 `orders.status`가 변경될 때마다 이력 테이블에 기록하는 트리거를 만들 수 있어요.

```sql
CREATE OR REPLACE TRIGGER trg_orders_status_history
AFTER UPDATE OF status
ON orders
FOR EACH ROW
BEGIN
    INSERT INTO order_status_history (
        order_id,
        old_status,
        new_status,
        changed_at
    ) VALUES (
        :OLD.order_id,
        :OLD.status,
        :NEW.status,
        SYSDATE
    );
END;
/
```

이 트리거는 `orders` 테이블의 `status` 컬럼이 변경된 후 실행돼요. 그리고 변경된 각 주문마다 이전 상태와 새로운 상태를 `order_status_history`에 저장합니다.

테스트해보면 이런 흐름이에요.

```sql
UPDATE orders
   SET status = 'CANCELED',
       updated_at = SYSDATE
 WHERE order_id = 1;
```

이 SQL은 주문 상태만 바꾸는 것처럼 보이지만, 트리거 때문에 이력 테이블에도 자동으로 데이터가 쌓여요.

---

## 예제: 수정 시간 자동 갱신

트리거는 `updated_at` 같은 컬럼을 자동으로 관리할 때도 사용할 수 있어요.

```sql
CREATE OR REPLACE TRIGGER trg_orders_updated_at
BEFORE UPDATE
ON orders
FOR EACH ROW
BEGIN
    :NEW.updated_at := SYSDATE;
END;
/
```

이 트리거는 `orders` 테이블이 수정되기 전에 실행돼요. 그리고 변경될 행의 `updated_at` 값을 현재 시간으로 바꿔줍니다.

여기서는 `BEFORE UPDATE`를 사용했기 때문에 `:NEW.updated_at` 값을 직접 변경할 수 있어요.

반대로 `AFTER UPDATE`에서는 이미 변경이 끝난 뒤라 `:NEW` 값을 바꾸는 용도로 사용하면 안 돼요. `AFTER` 트리거는 보통 로그 저장, 후속 테이블 반영 같은 작업에 더 어울려요.

## 트리거 조회

생성된 트리거 목록은 데이터 딕셔너리 뷰에서 확인할 수 있어요.

현재 사용자의 트리거를 보고 싶다면 `USER_TRIGGERS`를 사용할 수 있어요.

```sql
SELECT trigger_name,
       table_name,
       triggering_event,
       status
  FROM user_triggers;
```

접근 가능한 전체 트리거를 보고 싶다면 `ALL_TRIGGERS`를 사용할 수 있어요.

```sql
SELECT *
  FROM all_triggers;
```

트리거 소스는 `USER_SOURCE`에서 확인할 수 있어요.

```sql
SELECT text
  FROM user_source
 WHERE name = 'TRG_ORDERS_STATUS_HISTORY'
 ORDER BY line;
```

Oracle에서는 오브젝트 이름이 기본적으로 대문자로 저장되기 때문에, 조회할 때 이름을 대문자로 넣는 편이 안전해요.

## 트리거 수정과 삭제

트리거 수정은 생성할 때와 똑같이 `CREATE OR REPLACE TRIGGER`를 사용하면 돼요.

```sql
CREATE OR REPLACE TRIGGER trg_orders_status_history
AFTER UPDATE OF status
ON orders
FOR EACH ROW
BEGIN
    INSERT INTO order_status_history (
        order_id,
        old_status,
        new_status,
        changed_at
    ) VALUES (
        :OLD.order_id,
        :OLD.status,
        :NEW.status,
        SYSDATE
    );
END;
/
```

삭제는 `DROP TRIGGER`를 사용해요.

```sql
DROP TRIGGER trg_orders_status_history;
```

잠깐 비활성화만 하고 싶다면 `ALTER TRIGGER`를 사용할 수 있어요.

```sql
ALTER TRIGGER trg_orders_status_history DISABLE;
ALTER TRIGGER trg_orders_status_history ENABLE;
```

운영 중에는 삭제보다 비활성화가 더 안전할 때도 있어요. 다시 켤 수 있고, 어떤 트리거가 있었는지도 남기 때문이에요.

## 트리거는 언제 쓰면 좋을까?

트리거는 DB 레벨에서 반드시 보장하고 싶은 자동 처리에 잘 맞아요.

대표적으로는 이런 경우가 있어요.

- 변경 이력 저장
- 감사 로그 기록
- 수정일 자동 갱신
- 특정 컬럼 변경 시 연관 테이블 반영
- 간단한 데이터 정합성 보조 검증

예를 들어 감사 로그는 애플리케이션에서 매번 빼먹지 않고 호출해야 하는 방식보다, DB에서 자동으로 남기는 방식이 더 안정적일 수 있어요.

하지만 모든 비즈니스 로직을 트리거에 넣는 건 위험해요.

트리거는 숨어서 실행되기 때문에, 애플리케이션 코드만 봐서는 전체 흐름을 파악하기 어렵습니다.

## 실무에서 조심할 점

트리거를 사용할 때는 몇 가지를 꼭 신경 써야 해요.

첫 번째는 성능이에요.

행 레벨 트리거는 변경되는 행마다 실행돼요. 한두 건일 때는 괜찮아 보여도, 대량 `UPDATE`나 `DELETE`에서는 수천 번, 수만 번 실행될 수 있어요.

```sql
UPDATE orders
   SET status = 'EXPIRED'
 WHERE status = 'READY';
```

이 쿼리가 10만 건을 바꾸면 `FOR EACH ROW` 트리거도 10만 번 실행될 수 있어요. 트리거 안에서 무거운 쿼리나 외부 연동에 가까운 작업을 하면 성능 문제가 커질 수 있습니다.

두 번째는 숨은 동작이에요.

개발자는 `orders`만 수정했다고 생각했는데, 트리거가 `order_status_history`나 다른 테이블까지 바꾸고 있을 수 있어요. 장애가 났을 때 원인을 찾기 어려워지는 이유가 여기에 있어요.

세 번째는 연쇄 실행이에요.

A 테이블 트리거가 B 테이블을 수정하고, B 테이블 트리거가 다시 C 테이블을 수정하는 구조가 되면 흐름이 복잡해져요. 이런 구조는 가능하면 피하는 게 좋아요.

네 번째는 트랜잭션이에요.

트리거는 보통 트리거를 발생시킨 SQL과 같은 트랜잭션 안에서 실행돼요. 트리거 안에서 오류가 발생하면 원래 실행하던 `INSERT`, `UPDATE`, `DELETE`도 실패할 수 있어요.

이 점은 장점이기도 하고 위험이기도 해요. 정합성을 지키는 데는 좋지만, 예상하지 못한 트리거 오류가 서비스 로직 전체를 실패시킬 수 있기 때문이에요.

## 정리

Oracle Trigger는 DB 이벤트에 반응해서 자동으로 실행되는 PL/SQL 블록이에요.

핵심만 다시 정리하면 이렇습니다.

- `INSERT`, `UPDATE`, `DELETE` 같은 DML 이벤트에 반응할 수 있다.
- `BEFORE`, `AFTER`로 실행 시점을 정한다.
- `FOR EACH ROW`를 쓰면 변경된 행마다 실행된다.
- 행 레벨 트리거에서는 `:OLD`, `:NEW`로 변경 전/후 값을 참조한다.
- 수정은 `CREATE OR REPLACE TRIGGER`, 삭제는 `DROP TRIGGER`로 한다.
- 감사 로그, 변경 이력, 수정일 자동 갱신 같은 용도에 잘 맞는다.
- 비즈니스 로직을 과하게 넣으면 흐름이 숨고 디버깅이 어려워진다.

트리거는 잘 쓰면 DB 정합성을 지키는 든든한 장치가 되지만, 많이 쓰면 시스템을 읽기 어렵게 만드는 숨은 로직이 될 수 있어요.

그래서 저는 트리거를 사용할 때 이렇게 기준을 잡는 편이 좋아 보여요.

> 애플리케이션의 핵심 비즈니스 흐름은 서비스 코드에 두고, DB가 반드시 자동으로 보장해야 하는 이력과 감사성 로직에 제한적으로 사용하기.

이 정도 기준을 잡아두면 트리거의 장점은 살리면서, 운영 중 디버깅 난이도가 갑자기 올라가는 일을 줄일 수 있을 것 같아요.
