# AES256 + Base64는 왜 같이 사용할까?
### 핀테크 개발자가 실무에서 자주 마주하는 암복호화 흐름 정리

핀테크 도메인에서 개발을 하다 보면 생각보다 자주 마주치는 로직이 있습니다.

예를 들면:

- CI/DI 암호화
- 계좌번호 암호화
- 예금주명 보호 처리
- 외부 금융기관 전문 통신
- PG 연동
- 회원정보조회 API
- 결제 승인/취소 요청 데이터 보호

같은 것들입니다.

특히 금융권이나 결제 시스템에서는 개인정보나 민감 데이터를 평문으로 주고받는 경우가 거의 없기 때문에, AES256 암복호화 로직을 자주 접하게 됩니다.

그런데 실무 코드를 보다 보면 이런 흐름을 많이 보게 됩니다.

```java
AES256 Encrypt
→ Base64 Encode
```

처음 보면:

> “암호화했는데 왜 또 Base64를 하지?”

라는 의문이 들 수 있습니다.

오늘은 이 흐름이 왜 필요한지,  
각 단계에서 문자열이 어떻게 변하는지까지 실무 관점으로 자세히 정리해보겠습니다.

---

# 전체 흐름 먼저 보기

실무에서는 보통 이런 흐름으로 동작합니다.

```text
평문(String)
 ↓
AES256 Encrypt
 ↓
암호문(byte[])
 ↓
Base64 Encode
 ↓
전송 가능한 문자열(String)
```

복호화는 반대로 진행됩니다.

```text
Base64 문자열
 ↓
Base64 Decode
 ↓
암호문(byte[])
 ↓
AES256 Decrypt
 ↓
원본 문자열(String)
```

---

# 1. AES256은 실제로 무엇을 하는 걸까?

AES는 대표적인 대칭키 암호화 알고리즘입니다.

AES256은:
- AES 알고리즘 사용
- 256bit 길이의 Key 사용

을 의미합니다.

실제로 중요한 포인트는 이것입니다.

> AES의 결과물은 "문자열"이 아니라 byte[] 라는 점

예제를 보겠습니다.

---

# 예제 평문

```text
userCi=CI-123456789
```

우리가 보기엔 그냥 문자열입니다.

하지만 AES는 문자열을 직접 암호화하지 않습니다.

내부적으로는 먼저 byte[] 로 변환합니다.

```java
byte[] plainBytes =
    plainText.getBytes(StandardCharsets.UTF_8);
```

실제로는 이런 느낌입니다.

```text
[117, 115, 101, 114, 67, 105 ...]
```

그리고 AES Encrypt를 수행하면 결과는 사람이 읽을 수 없는 바이너리 데이터가 됩니다.

예시:

```text
[-12, 44, -98, 0, 127, ...]
```

즉:

- 문자열 아님
- UTF-8 보장 안됨
- 그대로 JSON/HTTP 넣기 위험
- 일부 문자는 깨질 수 있음

상태가 됩니다.

---

# 2. 왜 Base64를 사용하는 걸까?

여기서 등장하는 게 Base64입니다.

Base64의 역할은 단 하나입니다.

> byte[] 데이터를 안전한 문자열로 변환

즉:

```java
byte[] encryptedBytes = encrypt(...);

String base64 =
    Base64.getEncoder()
          .encodeToString(encryptedBytes);
```

결과:

```text
QWxhZGRpbjpvcGVuIHNlc2FtZQ==
```

이제는:
- 문자열 형태
- JSON 저장 가능
- HTTP 전송 가능
- 로그 출력 가능
- DB 저장 가능

상태가 됩니다.

---

# 많은 개발자가 헷갈리는 부분

Base64는 암호화가 아닙니다.

이건 정말 중요합니다.

AES:
- 보안 목적
- 복호화 키 필요

Base64:
- 단순 문자열 변환
- 누구나 decode 가능

예를 들어:

```text
SGVsbG8=
```

는 그냥:

```text
Hello
```

입니다.

즉:

| 기술 | 역할 |
|---|---|
| AES256 | 실제 암호화 |
| Base64 | 바이너리를 문자열로 포장 |

이라고 이해하면 됩니다.

---

# 3. 왜 암호문 byte[]를 String으로 바로 만들면 안될까?

실무에서 종종 이런 코드를 보게 됩니다.

```java
String encrypted =
    new String(encryptedBytes);
```

이건 굉장히 위험할 수 있습니다.

왜냐하면 암호문은 UTF-8 문자열이 아니기 때문입니다.

즉:
- 깨질 수 있음
- 일부 바이트 유실 가능
- 복호화 실패 가능
- 운영 환경에 따라 다르게 동작 가능

문제가 발생합니다.

특히:
- Linux
- Windows
- JVM Charset
- 서버 locale

차이로 인해 예상치 못한 장애가 발생하기도 합니다.

그래서 실무에서는 반드시 Base64를 사용해서 문자열화합니다.

---

# 실무 예제 코드 (Java)

아래는 가장 많이 사용하는 형태의 예제입니다.

---

# AES256 Encrypt + Base64 Encode

```java
import javax.crypto.Cipher;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.util.Base64;

public class AesExample {

    private static final String KEY =
            "12345678901234567890123456789012";

    public static void main(String[] args) throws Exception {

        String plainText = "userCi=CI-123456789";

        System.out.println("원본 문자열:");
        System.out.println(plainText);

        String encrypted = encrypt(plainText);

        System.out.println("\n암호화 + Base64 결과:");
        System.out.println(encrypted);

        String decrypted = decrypt(encrypted);

        System.out.println("\n복호화 결과:");
        System.out.println(decrypted);
    }

    public static String encrypt(String plainText)
            throws Exception {

        SecretKeySpec keySpec =
                new SecretKeySpec(
                        KEY.getBytes(StandardCharsets.UTF_8),
                        "AES"
                );

        Cipher cipher =
                Cipher.getInstance("AES/ECB/PKCS5Padding");

        cipher.init(Cipher.ENCRYPT_MODE, keySpec);

        byte[] encryptedBytes =
                cipher.doFinal(
                        plainText.getBytes(StandardCharsets.UTF_8)
                );

        return Base64.getEncoder()
                     .encodeToString(encryptedBytes);
    }

    public static String decrypt(String encryptedText)
            throws Exception {

        SecretKeySpec keySpec =
                new SecretKeySpec(
                        KEY.getBytes(StandardCharsets.UTF_8),
                        "AES"
                );

        Cipher cipher =
                Cipher.getInstance("AES/ECB/PKCS5Padding");

        cipher.init(Cipher.DECRYPT_MODE, keySpec);

        byte[] decodedBytes =
                Base64.getDecoder()
                      .decode(encryptedText);

        byte[] decryptedBytes =
                cipher.doFinal(decodedBytes);

        return new String(
                decryptedBytes,
                StandardCharsets.UTF_8
        );
    }
}
```

# 실행 흐름을 눈으로 이해해보기

예를 들어:

```text
userCi=CI-123456789
```

이 문자열이 있다고 가정해봅시다.

---

## 1단계 — UTF-8 Byte 변환

```text
[117, 115, 101, 114 ...]
```

---

## 2단계 — AES Encrypt

```text
[-34, 12, 99, -122 ...]
```

이미 사람이 읽을 수 없는 바이너리 상태입니다.

---

## 3단계 — Base64 Encode

```text
f3FaQk9xTnA1S...
```

드디어:
- 문자열
- HTTP 전송 가능
- JSON 저장 가능

한 상태가 됩니다.

---

# 복호화는 왜 Base64 Decode부터 할까?

암호화 결과는 실제 암호문이 아닙니다.

정확히는:

> 암호문 byte[] 를 Base64 문자열로 바꾼 결과

입니다.

그래서 복호화 시에는:

```java
Base64 Decode
→ AES Decrypt
```

순서로 진행해야 합니다.

---

# 실무에서 자주 마주하는 추가 포인트

## 1. URL 파라미터 전달 시 문제

Base64 문자열에는:

```text
+
/
=
```

문자가 포함될 수 있습니다.

그래서 URL Query Parameter로 전달 시 깨질 수 있습니다.

이럴 때는:

```java
Base64.getUrlEncoder()
```

사용하기도 합니다.

---

## 2. UTF-8은 항상 명시하자

실무에서는 반드시:

```java
StandardCharsets.UTF_8
```

명시하는 습관이 중요합니다.

특히 금융권 서버는:
- Linux
- AIX
- Windows
- 서로 다른 JVM

환경이 섞여 있는 경우가 많아서 charset 이슈가 실제 장애로 이어지기도 합니다.

---

## 3. ECB는 실무에서 지양하기도 한다

위 예제는 이해를 위해 ECB를 사용했지만,
실제 운영에서는 보통:

```text
AES/CBC/PKCS5Padding
```

혹은

```text
AES/GCM/NoPadding
```

방식을 더 많이 사용합니다.

특히 CBC에서는 IV(Initialization Vector) 관리도 매우 중요합니다.

실무에서는 이런 형태도 자주 봅니다.

```text
Base64(IV + 암호문)
```

# 마무리

정리하면:

| 단계 | 역할 |
|---|---|
| UTF-8 변환 | 문자열 → byte[] |
| AES256 Encrypt | 실제 암호화 |
| Base64 Encode | 안전한 문자열 변환 |
| Base64 Decode | 문자열 → byte[] 복원 |
| AES256 Decrypt | 원문 복호화 |

즉:

> AES는 보안을 위한 기술이고  
> Base64는 안전하게 전달하기 위한 기술입니다.

핀테크/결제 도메인에서는 이런 흐름이 정말 자주 등장합니다.

특히:
- 전문 통신
- 회원정보조회
- CI/DI 암호화
- 계좌 검증
- 결제 승인 데이터 보호

같은 영역에서는 거의 기본처럼 사용됩니다.

처음에는 단순히 “암호화 후 Base64 처리” 정도로만 보였던 코드도, 내부 흐름을 이해하고 보면 왜 저 순서가 필요한지 훨씬 명확하게 보이게 됩니다.
