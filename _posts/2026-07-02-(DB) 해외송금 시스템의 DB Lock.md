안녕하세요. 결제와 정산 도메인을 다루는 백엔드 엔지니어 곽철민이에요.

해외송금 시스템을 만들다 보면, 버튼 한 번이 단순한 요청 하나로 끝나지 않는다는 걸 금방 알게 돼요.

사용자가 100만 원을 베트남으로 송금한다고 해볼게요. 서버는 환율을 적용하고, 수수료를 계산하고, 고객의 연간 송금 한도를 확인하고, 외부 지급 사업자에 거래를 생성해요. 그리고 이 모든 과정은 돈과 연결되어 있어요.

그래서 작은 동시성 문제도 꽤 큰 장애가 될 수 있어요.

예를 들어 고객의 남은 송금 한도가 1,000달러라고 해볼게요. 그런데 거의 동시에 700달러 송금 요청이 두 번 들어왔어요.

두 요청이 각각 같은 잔여 한도를 읽고 이렇게 판단하면 어떻게 될까요?

> 아직 1,000달러가 남아 있으니 700달러 송금 가능

각 요청만 놓고 보면 맞는 판단이에요. 하지만 둘 다 성공하면 총 1,400달러가 예약돼요. 남은 한도보다 400달러를 더 쓴 셈이죠.

이런 문제를 막기 위해 DB Lock을 사용해요.

## Lock은 무엇을 지키는 걸까요

DB Lock은 데이터를 못 건드리게 막는 기술이라기보다, 동시에 바뀌면 안 되는 데이터를 순서대로 바꾸게 만드는 장치에 가까워요.

금융 시스템에는 이런 데이터가 많아요.

- 고객의 송금 한도
- 계좌 잔액
- 포인트 잔액
- 거래 상태
- 외부 거래번호 매핑 정보

이 데이터들은 대부분 "읽고 판단하고 변경하는" 흐름을 가져요.

```text
1. 현재 값을 읽는다.
2. 가능한지 판단한다.
3. 값을 변경한다.
```

문제는 1번과 3번 사이에 다른 요청이 끼어들 수 있다는 점이에요.

락은 바로 이 구간을 보호해줘요.

## 예제 상황: 해외송금 한도 차감

예제 테이블을 하나 만들어볼게요.

```sql
CREATE TABLE customer_remittance_limit (
    customer_id BIGINT PRIMARY KEY,
    annual_limit_usd DECIMAL(19, 2) NOT NULL,
    used_amount_usd DECIMAL(19, 2) NOT NULL,
    remaining_amount_usd DECIMAL(19, 2) NOT NULL,
    version BIGINT NOT NULL,
    updated_at TIMESTAMP NOT NULL
);
```

고객별 연간 송금 한도를 저장하는 테이블이에요.

송금 요청이 들어오면 서버는 `remaining_amount_usd`를 확인하고, 가능하면 `used_amount_usd`를 늘리고 `remaining_amount_usd`를 줄여요.

간단해 보이지만, 동시에 요청이 들어오면 조심해야 해요.

## 아무 락도 걸지 않으면 생기는 일

처음 상태가 이렇다고 해볼게요.

```text
customer_id = 1
remaining_amount_usd = 1000.00
```

동시에 두 요청이 들어와요.

```text
요청 A: 700달러 송금
요청 B: 700달러 송금
```

락이 없으면 두 요청은 모두 같은 값을 읽을 수 있어요.

```text
A: remaining_amount_usd = 1000 조회
B: remaining_amount_usd = 1000 조회

A: 700달러 가능하다고 판단
B: 700달러 가능하다고 판단
```

그다음 각각 차감해요.

결과적으로 한도가 초과될 수 있어요. 이런 문제를 Lost Update, Race Condition 같은 이름으로 불러요.

이제 MyBatis에서 어떻게 막을 수 있는지 하나씩 볼게요.

## 방법 1. 비관적 락

비관적 락은 이름 그대로 비관적으로 접근해요.

> 이 데이터는 동시에 수정될 가능성이 있어.
> 그러니 내가 처리하는 동안 다른 트랜잭션은 기다리게 하자.

대표적인 방법이 `SELECT ... FOR UPDATE`예요.

```sql
SELECT
    customer_id,
    annual_limit_usd,
    used_amount_usd,
    remaining_amount_usd,
    version,
    updated_at
FROM customer_remittance_limit
WHERE customer_id = #{customerId}
FOR UPDATE
```

이 쿼리를 트랜잭션 안에서 실행하면 해당 row에 쓰기 락이 걸려요. 같은 row를 수정하려는 다른 트랜잭션은, 앞선 트랜잭션이 끝날 때까지 기다려요.

MyBatis Mapper는 이렇게 작성할 수 있어요.

```java
@Mapper
public interface RemittanceLimitMapper {

    RemittanceLimit findByCustomerIdForUpdate(Long customerId);

    int increaseUsedAmount(
        @Param("customerId") Long customerId,
        @Param("amountUsd") BigDecimal amountUsd
    );
}
```

XML Mapper는 이렇게 둬요.

```xml
<select id="findByCustomerIdForUpdate" resultType="com.hf.fxremittanceapi.limit.RemittanceLimit">
    SELECT
        customer_id,
        annual_limit_usd,
        used_amount_usd,
        remaining_amount_usd,
        version,
        updated_at
    FROM customer_remittance_limit
    WHERE customer_id = #{customerId}
    FOR UPDATE
</select>

<update id="increaseUsedAmount">
    UPDATE customer_remittance_limit
    SET used_amount_usd = used_amount_usd + #{amountUsd},
        remaining_amount_usd = remaining_amount_usd - #{amountUsd},
        updated_at = CURRENT_TIMESTAMP
    WHERE customer_id = #{customerId}
</update>
```

서비스 코드는 `@Transactional` 안에서 실행해야 해요.

```java
@Service
public class RemittanceLimitService {

    private final RemittanceLimitMapper remittanceLimitMapper;

    public RemittanceLimitService(RemittanceLimitMapper remittanceLimitMapper) {
        this.remittanceLimitMapper = remittanceLimitMapper;
    }

    @Transactional
    public void reserveLimit(Long customerId, BigDecimal amountUsd) {
        RemittanceLimit limit = remittanceLimitMapper.findByCustomerIdForUpdate(customerId);

        if (limit.remainingAmountUsd().compareTo(amountUsd) < 0) {
            throw new BusinessException("송금 한도를 초과했습니다.");
        }

        remittanceLimitMapper.increaseUsedAmount(customerId, amountUsd);
    }
}
```

여기서 꼭 기억할 게 하나 있어요. `SELECT ... FOR UPDATE`만으로는 부족하다는 점이에요.

반드시 트랜잭션이 있어야 해요.

`@Transactional`이 없으면 쿼리 실행 직후 커넥션이 반환되면서 락도 바로 풀릴 수 있어요. 그러면 "락을 걸었다"고 생각했지만, 실제로는 보호 구간이 거의 없는 코드가 돼요.

비관적 락의 장점은 명확해요. 동시에 한 고객의 한도를 차감하는 상황을 순서대로 처리할 수 있어요.

대신 단점도 있어요. 뒤에 들어온 요청은 기다려야 해요. 트래픽이 몰리면 응답 시간이 늘 수 있고, 락을 오래 잡으면 장애로 이어질 수도 있어요.

그래서 비관적 락을 쓸 때는 트랜잭션 안에서 외부 API를 호출하지 않는 게 좋아요.

```java
@Transactional
public void badCase(Long customerId, BigDecimal amountUsd) {
    RemittanceLimit limit = remittanceLimitMapper.findByCustomerIdForUpdate(customerId);

    // 좋지 않은 예시
    // 락을 잡은 상태에서 외부 API를 호출하면 락 점유 시간이 길어져요.
    thunesClient.createTransaction(...);

    remittanceLimitMapper.increaseUsedAmount(customerId, amountUsd);
}
```

락을 잡은 상태에서는 DB 작업만 짧게 끝내는 편이 좋아요.

외부 API 호출은 락 밖으로 빼거나, 거래 상태를 먼저 만들고 이후 단계에서 처리하는 방식으로 분리하는 게 안전해요.

## 방법 2. 낙관적 락

낙관적 락은 반대로 생각해요.

> 충돌이 자주 일어나지는 않을 거야.
> 대신 충돌이 발생했는지 업데이트 시점에 확인하자.

낙관적 락에서는 보통 `version` 컬럼을 사용해요.

먼저 데이터를 조회해요.

```sql
SELECT
    customer_id,
    annual_limit_usd,
    used_amount_usd,
    remaining_amount_usd,
    version,
    updated_at
FROM customer_remittance_limit
WHERE customer_id = #{customerId}
```

그리고 업데이트할 때 조회 당시의 version을 조건에 포함해요.

```sql
UPDATE customer_remittance_limit
SET used_amount_usd = used_amount_usd + #{amountUsd},
    remaining_amount_usd = remaining_amount_usd - #{amountUsd},
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE customer_id = #{customerId}
  AND version = #{version}
  AND remaining_amount_usd >= #{amountUsd}
```

여기서 핵심은 `UPDATE` 결과 건수예요.

성공하면 `1`이 반환돼요. 누군가 먼저 수정해서 version이 바뀌었거나 잔여 한도가 부족하면 `0`이 반환되고요.

Mapper는 이렇게 작성할 수 있어요.

```java
@Mapper
public interface RemittanceLimitMapper {

    RemittanceLimit findByCustomerId(Long customerId);

    int tryIncreaseUsedAmount(
        @Param("customerId") Long customerId,
        @Param("amountUsd") BigDecimal amountUsd,
        @Param("version") Long version
    );
}
```

XML은 이렇게 둬요.

```xml
<select id="findByCustomerId" resultType="com.hf.fxremittanceapi.limit.RemittanceLimit">
    SELECT
        customer_id,
        annual_limit_usd,
        used_amount_usd,
        remaining_amount_usd,
        version,
        updated_at
    FROM customer_remittance_limit
    WHERE customer_id = #{customerId}
</select>

<update id="tryIncreaseUsedAmount">
    UPDATE customer_remittance_limit
    SET used_amount_usd = used_amount_usd + #{amountUsd},
        remaining_amount_usd = remaining_amount_usd - #{amountUsd},
        version = version + 1,
        updated_at = CURRENT_TIMESTAMP
    WHERE customer_id = #{customerId}
      AND version = #{version}
      AND remaining_amount_usd >= #{amountUsd}
</update>
```

서비스 코드는 이렇게 돼요.

```java
@Service
public class RemittanceLimitService {

    private final RemittanceLimitMapper remittanceLimitMapper;

    public RemittanceLimitService(RemittanceLimitMapper remittanceLimitMapper) {
        this.remittanceLimitMapper = remittanceLimitMapper;
    }

    @Transactional
    public void reserveLimitWithOptimisticLock(Long customerId, BigDecimal amountUsd) {
        RemittanceLimit limit = remittanceLimitMapper.findByCustomerId(customerId);

        int updated = remittanceLimitMapper.tryIncreaseUsedAmount(
            customerId,
            amountUsd,
            limit.version()
        );

        if (updated == 0) {
            throw new BusinessException("한도 정보가 변경되었습니다. 다시 시도해주세요.");
        }
    }
}
```

낙관적 락은 기다리지 않아요. 그래서 비관적 락보다 처리량이 좋을 수 있어요.

대신 충돌이 발생하면 실패해요. 실패한 요청은 재시도하거나, 사용자에게 다시 시도하라고 안내해야 해요.

충돌이 적은 데이터에는 잘 맞아요. 하지만 한 고객이 같은 순간 여러 송금 요청을 보내는 상황처럼 충돌 가능성이 높고 실패 처리가 민감한 흐름에서는 신중해야 해요.

## 더 단순한 방법: 조건부 UPDATE

한도 차감처럼 단순한 작업은 조회 없이 한 번의 `UPDATE`로 처리할 수도 있어요.

```sql
UPDATE customer_remittance_limit
SET used_amount_usd = used_amount_usd + #{amountUsd},
    remaining_amount_usd = remaining_amount_usd - #{amountUsd},
    updated_at = CURRENT_TIMESTAMP
WHERE customer_id = #{customerId}
  AND remaining_amount_usd >= #{amountUsd}
```

이 쿼리는 잔여 한도가 충분할 때만 차감해요.

결과 건수가 `1`이면 성공이고, `0`이면 한도 부족이에요.

```java
@Transactional
public void reserveLimitAtomically(Long customerId, BigDecimal amountUsd) {
    int updated = remittanceLimitMapper.decreaseRemainingAmountIfEnough(customerId, amountUsd);

    if (updated == 0) {
        throw new BusinessException("송금 한도를 초과했습니다.");
    }
}
```

이 방식은 꽤 실용적이에요.

DB의 `UPDATE` 자체가 row 단위로 원자적으로 실행되기 때문에, 단순 차감에는 좋은 선택지가 될 수 있어요. 읽고 판단하고 수정하는 과정을 애플리케이션에서 나누지 않고 DB에 맡기는 방식이죠.

다만 판단에 필요한 조건이 많아지면 쿼리가 복잡해질 수 있어요.

예를 들어 KYC 등급, 일 한도, 월 한도, 연 한도, 거래 상태, 외부 보고 대상 여부를 모두 함께 판단해야 한다면, 서비스 레이어에서 명시적으로 읽고 검증하는 방식이 더 읽기 쉬울 수 있어요.

## @Transactional은 어디까지 묶어야 할까요

락을 이야기할 때 `@Transactional`을 빼놓기 어려워요.

락은 트랜잭션과 함께 동작해요. 트랜잭션이 끝나면 락도 풀리고요.

그래서 보호하고 싶은 구간을 정확히 트랜잭션 안에 넣어야 해요.

```java
@Transactional
public void reserveLimit(Long customerId, BigDecimal amountUsd) {
    RemittanceLimit limit = remittanceLimitMapper.findByCustomerIdForUpdate(customerId);

    validateLimit(limit, amountUsd);

    remittanceLimitMapper.increaseUsedAmount(customerId, amountUsd);
}
```

반대로 트랜잭션 안에 너무 많은 걸 넣어도 문제예요.

```java
@Transactional
public void submitRemittance(Long customerId, BigDecimal amountUsd) {
    reserveLimit(customerId, amountUsd);
    createTransactionInThunes();
    sendNotification();
}
```

이 코드는 위험해요.

외부 API 호출과 알림 발송이 트랜잭션 안에 들어가 있어요. 외부 API가 느려지면 DB 락도 같이 오래 잡혀요. 그러면 다른 송금 요청이 대기하게 되고요.

금융 도메인에서는 트랜잭션을 길게 잡고 싶은 유혹이 있어요. 한 번에 묶으면 안전해 보이거든요.

하지만 실제로는 반대일 때가 많아요. 트랜잭션은 짧고 명확해야 해요.

DB에서 지켜야 하는 정합성은 DB 트랜잭션으로 보호하고, 외부 연동은 상태를 나누고 멱등키를 두고 실패했을 때 복구할 수 있게 설계하는 게 좋아요.

## 비관적 락과 낙관적 락 중 무엇을 써야 할까요

정답은 없어요. 데이터의 성격에 따라 달라져요.

비관적 락이 잘 맞는 경우가 있어요.

- 충돌 가능성이 높아요.
- 실패 후 재시도가 사용자 경험에 좋지 않아요.
- 한 번 잘못 차감되면 복구 비용이 커요.
- 송금 한도, 잔액처럼 돈과 직접 연결돼요.

낙관적 락이 잘 맞는 경우도 있어요.

- 충돌이 드물어요.
- 실패해도 재시도하면 돼요.
- 락 대기 시간을 줄이고 싶어요.
- 조회가 많고 수정이 상대적으로 적어요.

조건부 UPDATE가 잘 맞는 경우도 있어요.

- 검증 조건이 단순해요.
- 한 번의 SQL로 판단과 변경을 끝낼 수 있어요.
- 업데이트 결과 건수만으로 성공/실패를 판단할 수 있어요.

해외송금 한도 차감은 보통 비관적 락이나 조건부 UPDATE를 먼저 검토할 만해요. 돈과 직접 연결되고, 초과 차감이 발생하면 후처리가 번거롭기 때문이에요.

다만 모든 곳에 비관적 락을 걸면 시스템이 느려져요. 락은 정합성을 지키는 도구지만, 동시에 병목을 만드는 도구이기도 하거든요.

## 금융 도메인에서는 락만으로 부족해요

DB Lock은 중요해요. 하지만 락 하나로 금융 거래의 정합성이 완성되지는 않아요.

송금 시스템에서는 보통 여러 장치가 함께 필요해요.

첫째, 멱등키가 필요해요.

사용자가 송금 버튼을 두 번 누르거나, 네트워크 문제로 같은 요청이 재시도될 수 있어요. 이때 `Idempotency-Key`를 기준으로 같은 요청을 한 번만 처리해야 해요.

둘째, 상태 전이가 필요해요.

송금은 단순히 성공/실패만 있는 작업이 아니에요.

```text
DRAFT -> QUOTED -> CREATED -> CONFIRMED -> IN_PROGRESS -> COMPLETED
```

이런 식으로 상태를 나누고, 허용된 방향으로만 이동하게 해야 해요. 완료된 거래가 다시 진행 중으로 돌아가면 안 되겠죠.

셋째, 유니크 제약이 필요해요.

외부 거래번호, 내부 주문번호, 멱등키 같은 값은 DB 차원에서도 중복을 막아야 해요. 애플리케이션 검증만으로는 동시성을 완전히 막기 어렵거든요.

넷째, 보상 처리가 필요해요.

외부 지급 사업자 요청은 성공했는데 내부 상태 업데이트가 실패할 수 있어요. 반대로 내부 한도는 예약했는데 외부 거래 생성이 실패할 수도 있고요. 이런 경우를 위해 상태 복구, 재처리, 취소, 환불 흐름이 있어야 해요.

락은 이 중 하나예요.

중요하지만, 전부는 아니에요.

## 정리하며

DB Lock은 동시에 바뀌면 안 되는 데이터를 지키기 위한 장치예요.

Spring과 MyBatis를 사용하면 락이 더 명확하게 보여요. JPA 어노테이션 뒤에 숨지 않고, SQL로 직접 드러나거든요.

비관적 락은 `SELECT ... FOR UPDATE`로 row를 잠그고 순서대로 처리해요. 낙관적 락은 `version` 컬럼으로 충돌을 감지하고요. 조건부 UPDATE는 판단과 변경을 하나의 SQL로 끝내요.

해외송금 같은 금융 도메인에서는 "빠르게 처리하는 것"만큼이나 "틀리지 않게 처리하는 것"이 중요해요.

잔여 한도 1,000달러에서 700달러 송금 요청 두 개가 동시에 들어왔을 때, 시스템은 둘 중 하나를 기다리게 하거나 하나를 실패시켜야 해요.

둘 다 성공시키는 시스템은 빠른 시스템이 아니라 위험한 시스템이에요.

락은 그 위험을 줄이는 가장 기본적인 도구예요.
