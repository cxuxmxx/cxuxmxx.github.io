안녕하세요. 오늘은 Kafka를 이용해서 비동기 송금 시스템을 구성할 때 어떤 점을 고려해야 하는지 정리해보려고 해요.

송금 시스템에 Kafka를 붙인다고 하면 보통 이런 구조를 떠올리기 쉬워요.

```text
송금 완료
  -> Kafka 이벤트 발행
      -> Consumer가 후처리
```

큰 방향은 맞아요.

하지만 송금 도메인에서는 이 정도로만 이해하면 위험할 수 있어요. 송금은 단순히 메시지를 주고받는 시스템이 아니라, 돈의 상태를 정확하게 관리해야 하는 시스템이기 때문이에요.

Kafka를 쓴다고 해서 송금 정합성이 자동으로 보장되지는 않아요. Kafka의 Exactly Once를 사용한다고 해서 Oracle DB, Thunes API, ORIS 보고 요청까지 정확히 한 번만 실행되는 것도 아니에요.

그래서 송금 시스템에서 가장 먼저 잡아야 하는 기준은 이거예요.

> 송금 원장은 Oracle DB가 책임지고, Kafka는 확정된 상태 변화를 다른 시스템에 전달한다.

이 기준을 잡고 가야 Kafka를 안전하게 사용할 수 있어요.

---

## 송금 시스템에서 Kafka는 어디에 쓰면 좋을까?

Kafka는 모든 로직을 비동기로 바꾸기 위한 도구가 아니에요.

송금 시스템에서는 Kafka로 처리해도 되는 영역과, Kafka로 처리하면 위험한 영역을 나눠서 봐야 해요.

Kafka를 적용하기 좋은 영역은 이런 것들이에요.

- 송금 상태 변경 이벤트 전파
- ORIS 보고 요청
- 고객 알림 발송
- 정산 시스템 전달
- 이상거래 탐지
- 운영 모니터링 이벤트 수집
- 데이터웨어하우스 적재

이런 작업들은 송금이 확정된 뒤에 실행되는 후처리에 가까워요. 조금 늦게 처리되더라도 원장 정합성이 깨지지 않는 작업들이죠.

반대로 처음부터 Kafka로 빼면 위험한 영역도 있어요.

- 송금 한도 검증
- 중복 송금 검증
- 송금 원장 상태 변경
- 외부 송금 API의 실시간 요청과 응답
- 사용자에게 즉시 알려줘야 하는 성공·실패 결과
- 잔액 차감처럼 강한 정합성이 필요한 처리

이런 로직은 DB 트랜잭션 안에서 명확하게 처리하는 편이 안전해요.

즉 Kafka는 송금 자체를 처리하는 도구라기보다, 송금이 확정된 뒤 필요한 후속 작업을 안정적으로 분리하는 도구에 가까워요.

## 전체 구조

기본 구조는 이렇게 가져갈 수 있어요.

```text
송금 승인 API
  -> Oracle 트랜잭션 시작
      -> 송금 원장 상태 변경
      -> 거래 이력 저장
      -> Outbox 이벤트 저장
  -> Commit

Outbox Publisher
  -> Outbox 이벤트 조회
  -> Kafka 발행

Kafka Consumer
  -> ORIS 보고
  -> 알림 발송
  -> 정산 시스템 전달
  -> 모니터링 적재
```

여기서 핵심은 송금 원장 변경과 이벤트 저장을 같은 DB 트랜잭션으로 묶는 거예요.

이 구조를 `Transactional Outbox Pattern`이라고 해요.

왜 이런 구조가 필요할까요?

아래 코드를 보면 얼핏 괜찮아 보여요.

```java
@Transactional
public void confirmRemittance(ConfirmCommand command) {
    remittanceRepository.updateConfirmed(command.ordId());

    kafkaTemplate.send(
            "rmt.remittance-events.v1",
            command.ordId(),
            new RemittanceConfirmedEvent(...)
    );
}
```

하지만 이 코드는 실무에서 위험할 수 있어요.

`@Transactional`은 Oracle 트랜잭션을 보장할 뿐이에요. Kafka 발행까지 하나의 트랜잭션으로 묶어주지는 않아요.

그래서 이런 상황이 생길 수 있어요.

```text
Oracle Commit 성공
Kafka 발행 실패
```

이 경우 송금은 완료됐는데 후처리 이벤트는 사라져요.

반대 상황도 가능해요.

```text
Kafka 발행 성공
Oracle Commit 실패
```

이 경우 실제로 확정되지 않은 송금 이벤트가 외부 시스템에 전달될 수 있어요.

송금 시스템에서는 둘 다 치명적이에요. 그래서 Kafka로 바로 보내지 않고, 먼저 DB에 Outbox 이벤트를 저장하는 구조가 필요해요.

---

## Transactional Outbox Pattern

Outbox Pattern의 핵심은 단순해요.

> 업무 데이터 변경과 이벤트 저장을 같은 DB 트랜잭션으로 묶는다.

예를 들어 송금 확정 로직은 이렇게 만들 수 있어요.

```java
@Transactional
public void confirmRemittance(ConfirmCommand command) {
    remittanceRepository.updateConfirmed(command.ordId());

    remittanceTransactionRepository.insertConfirmHistory(
            command.ordId(),
            command.txnId()
    );

    RemittanceConfirmedEvent event = RemittanceConfirmedEvent.from(command);

    outboxRepository.insert(OutboxEvent.of(
            event.eventId(),
            "RemittanceConfirmed",
            event.ordId(),
            "rmt.remittance-events.v1",
            event
    ));
}
```

Outbox 테이블은 이런 식으로 시작할 수 있어요.

```sql
CREATE TABLE TB_OUTBOX_EVENT (
    EVENT_ID       VARCHAR2(36)   NOT NULL,
    EVENT_TYPE     VARCHAR2(100)  NOT NULL,
    AGGREGATE_ID   VARCHAR2(100)  NOT NULL,
    TOPIC_NAME     VARCHAR2(200)  NOT NULL,
    PAYLOAD        CLOB           NOT NULL,
    STATUS         VARCHAR2(20)   NOT NULL,
    CREATED_AT     DATE           NOT NULL,
    PUBLISHED_AT   DATE,
    RETRY_COUNT    NUMBER         DEFAULT 0,
    CONSTRAINT PK_OUTBOX_EVENT PRIMARY KEY (EVENT_ID)
);
```

이제 송금 원장 변경과 Outbox 저장은 같이 성공하거나 같이 실패해요.

```text
원장 변경 성공 + Outbox 저장 성공 = Commit
원장 변경 실패 또는 Outbox 저장 실패 = Rollback
```

그 다음 별도의 Publisher가 Outbox 테이블을 읽어서 Kafka로 발행해요.

```java
@Component
@RequiredArgsConstructor
public class OutboxPublisher {

    private final OutboxRepository outboxRepository;
    private final KafkaTemplate<String, RemittanceConfirmedEvent> kafkaTemplate;

    @Scheduled(fixedDelay = 1000)
    public void publish() {
        List<OutboxEvent> events = outboxRepository.findReadyEvents(100);

        for (OutboxEvent outbox : events) {
            RemittanceConfirmedEvent event = outbox.toEvent();

            kafkaTemplate.send(
                    outbox.topicName(),
                    outbox.aggregateId(),
                    event
            ).whenComplete((result, ex) -> {
                if (ex == null) {
                    outboxRepository.markPublished(outbox.eventId());
                } else {
                    outboxRepository.markFailed(outbox.eventId(), ex.getMessage());
                }
            });
        }
    }
}
```

여기서도 주의할 점이 있어요.

Publisher가 Kafka 발행에 성공한 뒤 `markPublished()`를 하기 전에 죽을 수 있어요. 그러면 애플리케이션이 재시작된 뒤 같은 이벤트가 다시 발행될 수 있어요.

그래서 Outbox를 사용해도 Consumer 멱등성은 반드시 필요해요.

Outbox는 이벤트 유실을 막기 위한 패턴이에요. 중복 처리를 완전히 없애주는 패턴은 아니에요.

## Topic과 Partition 설계

송금 이벤트 토픽은 이런 식으로 나눌 수 있어요.

```text
rmt.remittance-events.v1
rmt.oris-report-retry.v1
rmt.oris-report-dlt.v1
```

Kafka에서 꼭 알아야 하는 개념이 있어요.

> Kafka의 순서는 토픽 전체가 아니라 파티션 내부에서만 보장돼요.

예를 들어 같은 송금 건에 대해 이런 이벤트가 발생한다고 해볼게요.

```text
RemittanceCreated
RemittanceConfirmed
RemittanceCompleted
```

이 순서가 깨지면 안 돼요.

그러려면 같은 송금 건의 이벤트가 같은 파티션으로 들어가야 해요. Kafka는 key를 기준으로 파티션을 결정해요.

그래서 송금 시스템에서는 보통 `ordId`를 key로 사용해요.

```java
kafkaTemplate.send(
        "rmt.remittance-events.v1",
        event.ordId(),
        event
);
```

이렇게 하면 같은 `ordId`를 가진 이벤트는 같은 파티션에 들어가요. 따라서 같은 송금 건 안에서는 순서를 유지할 수 있어요.

단, 전체 송금 건의 순서가 보장되는 건 아니에요.

`ORD-1001`과 `ORD-2002`는 서로 다른 파티션에서 병렬로 처리될 수 있어요. 이게 Kafka를 사용하는 이유이기도 해요. 같은 송금 건은 순서를 지키고, 서로 다른 송금 건은 병렬로 처리할 수 있으니까요.

## Consumer Group

Consumer Group은 같은 일을 나눠서 처리하는 Consumer 묶음이에요.

예를 들어 `oris-report-worker`라는 Consumer Group이 있고, 토픽 파티션이 3개라고 해볼게요.

```text
Topic: rmt.remittance-events.v1
Partition: 3개

Consumer Group: oris-report-worker
Consumer Instance: 3개
```

그러면 Kafka는 파티션을 Consumer들에게 나눠줘요.

```text
Partition 0 -> Consumer A
Partition 1 -> Consumer B
Partition 2 -> Consumer C
```

Consumer를 4개로 늘리면 어떻게 될까요?

```text
Partition 0 -> Consumer A
Partition 1 -> Consumer B
Partition 2 -> Consumer C
Consumer D -> 할당 없음
```

파티션이 3개라면 같은 Consumer Group 안에서는 최대 3개 Consumer만 동시에 일할 수 있어요.

그래서 Consumer 수를 늘린다고 처리량이 계속 늘어나는 건 아니에요. 파티션 수와 처리량, 향후 확장 가능성을 같이 보고 설계해야 해요.

## 이벤트 모델

Kafka에 발행하는 이벤트는 “명령”이 아니라 “이미 일어난 사실”이어야 해요.

```text
명령: ORIS에 보고해라
이벤트: 송금이 확정되었다
```

이 둘은 달라요.

송금 확정 이벤트는 이런 형태로 만들 수 있어요.

```java
public record RemittanceConfirmedEvent(
        String eventId,
        String eventType,
        String eventVersion,
        String ordId,
        String txnId,
        String externalId,
        BigDecimal remitAmount,
        String remitCurrency,
        Instant occurredAt,
        String traceId
) {
}
```

각 필드는 이런 역할을 해요.

| 필드 | 설명 |
|---|---|
| eventId | 이벤트 중복 처리용 ID |
| eventType | 이벤트 종류 |
| eventVersion | 이벤트 스키마 버전 |
| ordId | 송금 주문 ID |
| txnId | 거래 ID |
| externalId | 외부 API 연동용 ID |
| occurredAt | 실제 사건 발생 시각 |
| traceId | 요청 추적 ID |

주의할 점은 개인정보예요.

Kafka 이벤트에는 개인정보를 너무 많이 넣지 않는 편이 좋아요.

예를 들어 이런 값들은 이벤트에 넣지 않는 게 안전해요.

- 주민등록번호
- 계좌번호
- 수취인 이름
- 전화번호
- 주소
- 인증 정보

필요하다면 Consumer가 `ordId`를 기준으로 DB에서 다시 조회하게 할 수 있어요. Kafka 이벤트는 여러 시스템에 복제될 수 있기 때문에, 처음부터 최소한의 정보만 담는 게 좋아요.

## Producer 설정

송금 시스템에서는 Producer 설정도 안정성을 우선해야 해요.

예시는 이렇습니다.

```yaml
spring:
  kafka:
    producer:
      acks: all
      properties:
        enable.idempotence: true
        max.in.flight.requests.per.connection: 5
        compression.type: zstd
```

`acks=all`은 Kafka Broker가 메시지를 충분히 복제한 뒤 성공으로 응답하게 하는 설정이에요.

`enable.idempotence=true`는 Producer 재시도로 인해 Kafka에 중복 기록될 가능성을 줄여줘요.

하지만 이 설정을 오해하면 안 돼요.

> Producer idempotence는 Consumer의 업무 중복 처리를 막아주지 않아요.

Consumer가 DB 처리를 끝낸 뒤 Offset Commit 전에 죽으면 같은 이벤트를 다시 받을 수 있어요. 그래서 Consumer 쪽 멱등성은 따로 구현해야 해요.

`KafkaTemplate.send()` 결과도 무시하면 안 돼요.

```java
CompletableFuture<SendResult<String, RemittanceConfirmedEvent>> future =
        kafkaTemplate.send(topic, event.ordId(), event);

future.whenComplete((result, ex) -> {
    if (ex == null) {
        log.info(
                "Kafka publish success. eventId={}, topic={}, partition={}, offset={}",
                event.eventId(),
                result.getRecordMetadata().topic(),
                result.getRecordMetadata().partition(),
                result.getRecordMetadata().offset()
        );
    } else {
        log.error("Kafka publish failed. eventId={}", event.eventId(), ex);
    }
});
```

송금 시스템에서는 “보냈다”보다 “어디에 기록됐는지 추적할 수 있다”가 더 중요해요.

## Consumer Offset

Consumer 처리 순서는 이렇게 가져가는 게 안전해요.

```text
1. 이벤트 수신
2. eventId 기준 중복 확인
3. 업무 DB 처리
4. DB Commit
5. Offset Commit
```

Offset은 Kafka가 “이 Consumer Group이 어디까지 읽었는지” 기억하는 위치예요.

만약 업무 처리 전에 Offset을 먼저 Commit하면 위험해요.

```text
Offset Commit 성공
업무 DB 처리 실패
```

이 경우 Kafka는 이미 처리한 이벤트라고 판단해요. 하지만 실제 업무 처리는 실패했어요.

반대로 DB Commit 후 Offset Commit 전에 서버가 죽으면 어떻게 될까요?

```text
DB Commit 성공
Offset Commit 실패
Consumer 재시작
같은 이벤트 재수신
```

이 경우 같은 이벤트가 다시 들어와요.

이건 예외적인 버그라기보다 Kafka를 쓰면 자연스럽게 발생할 수 있는 상황이에요. 그래서 Consumer는 같은 이벤트를 두 번 받아도 안전해야 해요.

이걸 멱등성이라고 해요.

## Consumer 멱등성

멱등성 테이블을 하나 두는 방식이 가장 이해하기 쉬워요.

```sql
CREATE TABLE TB_KAFKA_PROCESSED_EVENT (
    EVENT_ID        VARCHAR2(36)  NOT NULL,
    CONSUMER_GROUP  VARCHAR2(100) NOT NULL,
    PROCESSED_AT    DATE          NOT NULL,
    CONSTRAINT PK_KAFKA_PROCESSED_EVENT
        PRIMARY KEY (EVENT_ID, CONSUMER_GROUP)
);
```

Consumer는 업무 처리 전에 먼저 이 테이블에 `eventId`를 INSERT해요.

이미 존재하면 중복 이벤트예요. 그 경우 업무 처리를 다시 하지 않고 종료하면 돼요.

```java
@Service
@RequiredArgsConstructor
public class OrisReportService {

    private final ProcessedEventRepository processedEventRepository;
    private final OrisReportRepository orisReportRepository;

    @Transactional
    public void createReportRequest(RemittanceConfirmedEvent event) {
        boolean first = processedEventRepository.insertIfAbsent(
                event.eventId(),
                "oris-report-worker"
        );

        if (!first) {
            log.info("Duplicated event ignored. eventId={}", event.eventId());
            return;
        }

        orisReportRepository.insertPendingReport(
                event.ordId(),
                event.txnId(),
                event.externalId(),
                event.traceId()
        );
    }
}
```

중요한 건 `TB_KAFKA_PROCESSED_EVENT` INSERT와 실제 업무 처리를 같은 DB 트랜잭션으로 묶는 거예요.

그래야 이벤트 처리 여부와 업무 결과가 같이 Commit되거나 같이 Rollback돼요.

## ORIS 보고 Consumer 예시

Kafka Consumer는 이렇게 만들 수 있어요.

```java
@Component
@RequiredArgsConstructor
public class OrisReportConsumer {

    private final OrisReportService orisReportService;

    @KafkaListener(
            topics = "rmt.remittance-events.v1",
            groupId = "oris-report-worker"
    )
    public void listen(RemittanceConfirmedEvent event) {
        if (!"RemittanceConfirmed".equals(event.eventType())) {
            return;
        }

        orisReportService.createReportRequest(event);
    }
}
```

여기서 Consumer가 바로 ORIS API를 호출할 수도 있어요. 하지만 실무에서는 한 단계를 더 나누는 편이 좋아요.

```text
Kafka Event 수신
  -> ORIS_REPORT_PENDING 저장
  -> Commit
```

그 다음 별도 Worker가 ORIS API를 호출해요.

```text
ORIS_REPORT_PENDING 조회
  -> ORIS API 호출
  -> SUCCESS / UNKNOWN / FAILED 상태 저장
```

이렇게 나누면 Kafka 재처리와 외부 API 재시도를 분리할 수 있어요. 장애가 났을 때 어디까지 처리됐는지도 훨씬 보기 쉬워요.

---

## 외부 API Timeout

송금 시스템에서 가장 위험한 착각 중 하나가 있어요.

> Timeout이 났으니 실패다.

항상 그렇지는 않아요.

예를 들어 Thunes나 ORIS에 요청을 보냈다고 해볼게요.

```text
우리 서버 -> 외부사 요청 전송
외부사 -> 실제 처리 성공
우리 서버 <- 응답 수신 실패 또는 Timeout
```

우리 서버 입장에서는 Timeout이에요. 하지만 외부사에서는 이미 처리됐을 수 있어요.

이 상태에서 같은 요청을 바로 재시도하면 중복 송금이나 중복 보고가 생길 수 있어요.

그래서 상태 변경 API는 이렇게 처리하는 편이 안전해요.

```text
1. 내부 거래를 REQUESTING 상태로 저장
2. externalId 생성
3. 외부 API 호출
4. 성공 응답이면 CREATED 또는 CONFIRMED 처리
5. Timeout이면 FAILED가 아니라 UNKNOWN 처리
6. externalId로 외부 상태 조회
7. 실제 결과 확인 후 상태 확정
```

상태는 예를 들어 이렇게 가져갈 수 있어요.

```text
READY
REQUESTING
CREATED
CONFIRMED
UNKNOWN
FAILED
```

여기서 중요한 건 `UNKNOWN`이에요.

실패인지 성공인지 아직 모르는 상태를 시스템 안에 명확히 표현하는 거예요. 송금 시스템에서는 이 상태를 단순 예외로 뭉개면 안 돼요.

---

## RestClient 사용 시 주의할 점

Spring의 `RestClient`는 동기 Blocking HTTP Client예요. 요청을 보내고 응답을 기다리는 동안 서버 스레드를 점유해요.

그래서 Timeout 설정이 반드시 필요해요.

```java
@Bean
RestClient thunesRestClient(
        RestClient.Builder builder,
        ThunesProperties properties
) {
    HttpClient httpClient = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(3))
            .build();

    JdkClientHttpRequestFactory requestFactory =
            new JdkClientHttpRequestFactory(httpClient);

    requestFactory.setReadTimeout(Duration.ofSeconds(10));

    return builder.clone()
            .baseUrl(properties.baseUrl())
            .requestFactory(requestFactory)
            .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
            .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE)
            .build();
}
```

Timeout은 최소 두 가지를 봐야 해요.

- `connectTimeout`: 연결을 맺는 데 걸리는 시간 제한
- `readTimeout`: 연결 후 응답을 기다리는 시간 제한

재시도를 포함한 전체 시간도 계산해야 해요.

예를 들어 이렇게 설정했다고 해볼게요.

```text
Read timeout: 10초
Retry: 2회
Backoff: 1초, 2초
```

최악의 경우 전체 시간이 30초를 넘을 수 있어요. 그러면 Tomcat이나 JEUS의 요청 스레드가 오래 붙잡히게 돼요.

외부사가 느려지면 우리 서버까지 같이 느려질 수 있어요. 그래서 외부 API에는 Timeout, Retry, Circuit Breaker, Bulkhead 같은 보호 장치가 필요해요.

---

## POST 요청 재시도

조회 API는 비교적 재시도가 쉬워요.

```text
GET 거래 조회
GET 환율 조회
GET 지급기관 조회
```

하지만 상태를 바꾸는 API는 달라요.

```text
POST 송금 생성
POST 송금 승인
POST 결제 승인
POST 취소 요청
```

이런 요청은 자동 재시도가 위험해요.

재시도하려면 아래 조건 중 하나가 필요해요.

- 외부사가 Idempotency-Key를 지원한다.
- 동일 externalId 중복 요청을 거절한다.
- 거래 조회 API로 기존 처리 여부를 확인할 수 있다.
- 우리 쪽 요청 원장으로 중복 방지가 가능하다.
- API 명세가 동일 요청 재전송이 안전하다고 보장한다.

그렇지 않다면 Timeout이 났을 때 바로 재요청하면 안 돼요. 먼저 상태 조회로 실제 처리 여부를 확인해야 해요.

---

## Retry와 DLT

Consumer에서 예외가 발생했다고 모두 재시도하면 안 돼요.

예외는 나눠서 봐야 해요.

| 유형 | 예시 | 처리 |
|---|---|---|
| 일시적 오류 | DB 접속 실패, 외부 API 503, Timeout | 제한적 재시도 |
| 영구적 오류 | JSON 파싱 실패, 필수 필드 누락 | 즉시 DLT |
| 업무 오류 | 이미 보고 완료, 취소된 송금 | 정상 종료 또는 별도 상태 기록 |

잘못된 JSON은 백 번 재시도해도 성공하지 않아요. 반대로 일시적인 DB 오류는 몇 초 뒤 성공할 수 있어요.

DLT는 Dead Letter Topic이에요. 자동 복구가 어렵다고 판단된 이벤트를 별도로 보관하는 토픽이에요.

DLT에는 최소한 이런 정보가 있어야 해요.

- 원본 topic
- partition
- offset
- eventId
- ordId
- traceId
- 실패 시각
- 재시도 횟수
- 예외 타입
- 오류 메시지
- 원본 payload
- 재처리 상태

DLT는 실패 메시지 쓰레기통이 아니에요. 운영자가 복구할 수 있는 실패 원장이어야 해요.

---

## Exactly Once를 오해하면 안 돼요

Kafka에는 Exactly Once Semantics가 있어요. 하지만 이걸 “송금이 정확히 한 번만 처리된다”는 뜻으로 이해하면 안 돼요.

Kafka Exactly Once는 주로 Kafka 내부 흐름에 대한 이야기예요.

```text
Kafka에서 읽기
  -> 처리
  -> Kafka에 쓰기
  -> Consumer Offset 반영
```

하지만 송금 시스템에는 Kafka 밖의 작업이 많아요.

- Oracle DB 업데이트
- Thunes API 호출
- ORIS API 호출
- 알림 발송
- 정산 시스템 연동

Kafka Exactly Once를 켠다고 해서 Oracle 업데이트나 외부 REST API 호출까지 정확히 한 번만 실행되는 건 아니에요.

송금 시스템에서는 아래 조합이 현실적이에요.

```text
At-least-once 전달
+ Transactional Outbox
+ Consumer 멱등성
+ 외부 API 멱등키
+ 상태 기반 복구
```

실무에서는 이 방식이 가장 이해하기 쉽고 운영하기 좋아요.

---

## 모니터링

Kafka를 운영할 때 Consumer Lag만 보면 부족해요.

기술 지표는 이런 것들을 봐야 해요.

- Consumer Lag
- 초당 소비량
- 평균 처리 시간
- 최대 처리 시간
- Rebalance 횟수
- Producer 발행 실패율
- Broker ISR 변화
- Under Replicated Partition

업무 지표도 같이 봐야 해요.

- Outbox 미발행 건수
- 가장 오래된 Outbox 대기 시간
- DLT 건수
- 가장 오래된 DLT 이벤트 나이
- ORIS 보고 성공률
- 외부 API Timeout 수
- UNKNOWN 상태 거래 수
- 송금 완료 후 후처리 지연 시간

Lag이 늘어난다고 무조건 Consumer를 늘리면 안 돼요.

외부 API가 느려졌을 수도 있고, 특정 파티션에만 메시지가 몰렸을 수도 있어요. DB Lock 때문에 처리가 느려졌을 수도 있고요.

그래서 Lag은 항상 처리량, 처리 시간, 오류율, 업무 상태와 같이 봐야 해요.

---

## 테스트해야 하는 것들

Kafka 기반 송금 시스템은 정상 케이스보다 장애 케이스가 더 중요해요.

최소한 아래 시나리오는 테스트해야 해요.

- 같은 eventId 이벤트를 두 번 발행한다.
- DB Commit 후 Offset Commit 전에 Consumer를 종료한다.
- Outbox Publisher가 Kafka 발행 직후 죽는다.
- 잘못된 JSON 이벤트를 넣는다.
- 필수 필드가 없는 이벤트를 넣는다.
- Retry 후 성공하는 케이스를 검증한다.
- Retry를 모두 소진하면 DLT로 이동하는지 확인한다.
- 같은 ordId 이벤트 순서가 유지되는지 확인한다.
- Consumer 인스턴스를 늘렸을 때 파티션이 재분배되는지 확인한다.
- 외부 API Timeout 후 UNKNOWN 상태로 남는지 확인한다.
- UNKNOWN 상태 거래가 조회 API로 복구되는지 확인한다.

Testcontainers를 쓰면 실제 Kafka를 띄워 통합 테스트를 만들 수 있어요.

```java
@SpringBootTest
@Testcontainers
class RemittanceKafkaIntegrationTest {

    @Container
    static KafkaContainer kafka = new KafkaContainer(
            DockerImageName.parse("apache/kafka-native:3.8.0")
    );

    @Test
    void duplicatedEventShouldBeProcessedOnlyOnce() {
        RemittanceConfirmedEvent event = testEvent();

        kafkaTemplate.send("rmt.remittance-events.v1", event.ordId(), event);
        kafkaTemplate.send("rmt.remittance-events.v1", event.ordId(), event);

        await().untilAsserted(() -> {
            assertThat(orisReportRepository.countByEventId(event.eventId()))
                    .isEqualTo(1);
        });
    }
}
```

송금 시스템에서 테스트 통과의 기준은 단순히 Consumer가 메시지를 읽는 게 아니에요.

유실 없이, 중복 없이, 복구 가능하게 처리되는지가 더 중요해요.

## 운영 Runbook

Kafka를 도입하면 운영 절차도 같이 준비해야 해요.

Runbook에는 이런 내용이 들어가면 좋아요.

- Consumer Lag 급증 시 확인 순서
- 특정 Consumer Group 재시작 절차
- DLT 조회 방법
- DLT 재처리 승인 절차
- 재처리 전 중복 여부 확인 방법
- Offset 이동 기준과 승인 절차
- Outbox 적체 복구 방법
- 잘못된 이벤트 버전 배포 시 롤백 방법
- 외부 API 장애 시 Consumer 처리 전략
- 대량 재처리 시 외부사 호출량 제한 방법
- 개인정보 포함 이벤트 유출 대응 절차

특히 DLT 재처리는 조심해야 해요.

DLT 메시지를 다시 원본 토픽에 넣으면 실제 업무가 다시 실행될 수 있어요. 재처리 전에는 반드시 `eventId`, `ordId`, 현재 업무 상태, 기존 처리 이력을 확인해야 해요.

## 처음 도입한다면

처음부터 모든 송금 처리를 Kafka로 바꾸는 건 위험해요.

처음 도입 과제로는 아래 정도가 좋아요.

```text
송금 완료 후 ORIS 비동기 보고 시스템
```

구성 요소는 이렇게 잡을 수 있어요.

- 송금 승인 API
- Oracle 송금 원장
- Transactional Outbox
- Kafka Publisher
- RemittanceConfirmedEvent
- ORIS Report Consumer
- Consumer 멱등성 테이블
- Retry
- DLT
- traceId 전달
- Outbox 모니터링
- Consumer Lag 모니터링
- Testcontainers 통합 테스트

완료 기준은 명확해야 해요.

- 같은 이벤트를 10번 받아도 ORIS 보고 요청은 한 번만 생성된다.
- DB Commit 후 Consumer가 죽어도 재시작 후 안전하게 복구된다.
- Outbox Publisher가 Kafka 발행 직후 죽어도 이벤트가 유실되지 않는다.
- 잘못된 이벤트는 무한 재시도하지 않고 DLT로 이동한다.
- 같은 ordId의 이벤트 순서가 유지된다.
- traceId로 API 요청, Outbox, Kafka 이벤트, ORIS 보고를 추적할 수 있다.
- DLT 이벤트를 운영 절차에 따라 안전하게 재처리할 수 있다.
- 외부 API Timeout은 FAILED가 아니라 UNKNOWN으로 남고 조회로 복구된다.

## 정리

Kafka는 송금 시스템의 정합성을 대신 보장해주는 도구가 아니에요.

송금 시스템에서 Kafka를 잘 쓴다는 건 메시지를 빠르게 보내는 것보다, 책임 경계를 명확히 나누는 것에 가까워요.

핵심만 다시 정리하면 이렇습니다.

- 송금 원장은 Oracle DB가 책임진다.
- Kafka는 확정된 상태 변화를 전달한다.
- DB 변경과 이벤트 저장은 Outbox로 묶는다.
- Kafka 전달은 At-least-once를 전제로 한다.
- Consumer는 eventId 기준으로 멱등하게 만든다.
- 외부 API Timeout은 실패가 아니라 UNKNOWN 상태로 다룬다.
- Retry와 DLT는 운영자가 복구할 수 있는 구조로 설계한다.

Kafka는 잘 쓰면 송금 완료 이후의 보고, 알림, 정산, 모니터링을 안정적으로 분리할 수 있어요.

하지만 돈의 상태까지 Kafka에 맡기면 안 돼요. 돈의 상태는 원장이 책임지고, 이벤트 전달은 Kafka가 책임지고, 중복과 장애는 Consumer와 운영 절차가 책임져야 해요.

이 경계를 명확히 잡는 것이 Kafka 기반 비동기 송금 시스템의 출발점이라고 생각해요.
